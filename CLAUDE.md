# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`book-habit-nest` is a [NestJS](https://docs.nestjs.com) (TypeScript) backend for a book-reading-habit app, scaffolded via `@nestjs/cli`, using [Prisma](https://www.prisma.io) ORM against MySQL. It aggregates book metadata from external providers (Kakao, Aladin) and lets users track their own reading (`MyBook`), reading sessions (`ReadingLog`), one-line reviews with likes/comments (`MyBookReview`/`ReviewLike`/`ReviewComment`), tags, and reading goals.

## Architecture

- Standard NestJS module/controller/service pattern. Entry point is [src/main.ts](src/main.ts), which bootstraps `AppModule`, calls `app.enableShutdownHooks()` (so `PrismaService.onModuleDestroy`'s `$disconnect` actually runs on SIGTERM/SIGINT, not just on an explicit `app.close()`), sets a global `api` prefix, wires `helmet()` + the request-logging middleware + `cookie-parser`, a global `ValidationPipe` (`whitelist`, `transform`, `forbidNonWhitelisted`), and Swagger at `/api` (see `setUpMiddleware`/`setUpCors`/`setUpSwagger` in [src/main.ts](src/main.ts)). Listens on `PORT` env var (default 3000).
- [src/app.module.ts](src/app.module.ts) is the root module; new feature modules are registered here. `ConfigModule.forRoot` is wired with a Joi `validationSchema` ([src/config/env-validation.schema.ts](src/config/env-validation.schema.ts)) that fails fast at boot on missing/malformed required env vars (`DATABASE_URL`, `JWT_*_SECRET`/`JWT_*_EXPIRES_IN`, `CORS_ORIGINS`, `KAKAO_CLIENT_ID`/`KAKAO_CALLBACK_URL`) — `ALADIN_TTB_KEY`/`NL_CERT_KEY`/`KAKAO_REST_API` stay optional since existing code already treats them as such via `configService.get` (not `getOrThrow`). It also registers app-wide providers via `APP_INTERCEPTOR`/`APP_FILTER`/`APP_GUARD` — the `APP_GUARD` is `ThrottlerGuard` (`@nestjs/throttler`), giving every route a default rate limit (100 req/min); `AUTH_THROTTLE` in `auth.constants.ts` tightens this further for brute-force-prone endpoints (see "Auth" below).
- **Database**: [prisma/schema.prisma](prisma/schema.prisma) defines the MySQL schema; `DATABASE_URL` (see [.env.example](.env.example)) points at the `docker-compose.yml` MySQL service. [src/prisma/prisma.service.ts](src/prisma/prisma.service.ts) extends `PrismaClient` with Nest lifecycle hooks (`$connect`/`$disconnect`) and passes `log: ['query', 'warn', 'error']` to the `PrismaClient` constructor outside production (`log: ['warn', 'error']` in production) so the actual SQL is visible in dev logs — useful for spotting N+1s at runtime instead of only by code review. [src/prisma/prisma.module.ts](src/prisma/prisma.module.ts) is `@Global()` so any module can inject `PrismaService` without re-importing it. Prisma is pinned to an exact version (`prisma`/`@prisma/client` both `6.12.0`, not `^6.12.0`) because newer 6.13+ releases pull a vulnerable `deepmerge-ts` via `@prisma/config` — bump deliberately, not via a caret range.
  - Core domain: `Book` (canonical book record, keyed by unique `isbn`) — `User` — `MyBook` (a user's copy of a book: status/rating/progress, unique per `[userId, bookId]`) — `ReadingLog` (individual reading sessions under a `MyBook`, with `Quote`s) — `MyBookReview` (one public/private one-line review per `MyBook`) with `ReviewLike`/`ReviewComment` — `Tag`/`MyBookTag` — `ReadingGoal` (yearly or monthly target by `ReadingGoalMetric`). Several FKs deliberately skip `onDelete: Cascade` on `userId` to avoid MySQL "multiple cascade paths" errors where a cascade already reaches the same table via `MyBook` — see the comments in [prisma/schema.prisma](prisma/schema.prisma) before adding new cascades.
- **Standard response envelope** (`src/common/response`): every controller response is wrapped by `ResponseDtoInterceptor` (an `APP_INTERCEPTOR`) into `{ success, statusCode, message, data }` via `ResponseDto`, and every uncaught exception is normalized to the same shape by `ResponseExceptionFilter` (an `APP_FILTER`), keyed off `HttpException`. Use `@ResponseMessage('...')` to customize the success message. Because the wrapping happens in an interceptor, `@ApiOkResponse({ type: Dto })` alone would document the *unwrapped* body — use `@ApiResponseDto(Dto, { isArray? })` from the same folder instead, which wraps the schema in `ResponseDto` for Swagger.
- **Pagination** (`src/common/pagination`): `PaginationUtil.getSkipTake` / `getPaginationMeta` are the shared helpers for Prisma `skip`/`take` and building a `PaginationMeta` (page/total/hasNext/hasPrev); see usage in `KakaoBookSearchService`.
- **Prisma error helper** (`src/common/prisma-error.util.ts`): `PrismaErrorUtil.isUniqueConstraintViolation(error, field)` / `isRecordNotFound(error)` centralize P2002/P2025 detection so services can translate them into `ConflictException`/`NotFoundException` without duplicating the `error.meta?.target` string/array-checking logic.
- **Request logging** (`src/common/logging/logging.middleware.ts`): `loggingMiddleware` logs every request as `` `[${requestId}] ${method} ${url} ${statusCode} ${durationMs}ms` `` via `response.on('finish', ...)`. It's registered as plain Express middleware in `main.ts`, deliberately **not** an `APP_INTERCEPTOR` — interceptors only run for requests that already passed Guards, so a `NestInterceptor` here would silently miss 401s (`AccessTokenGuard`) and 429s (`ThrottlerGuard`); middleware runs first in the pipeline and catches every request regardless of how it's rejected. It also assigns `request.id` (a `randomUUID()`, typed via the global `Express.Request` augmentation in [src/types/express.d.ts](src/types/express.d.ts)) and echoes it back as the `X-Request-Id` response header; `ResponseExceptionFilter` logs the same `request.id` alongside a 5xx stack trace, so a user-reported timestamp/id can be matched to both the access-log line and the error's stack trace.
- **Book-page validation** (`src/common/book-page.util.ts`): `assertWithinTotalPage(page, totalPage, message)` centralizes the "page can't exceed the book's total page count" rule (no-op when `totalPage` is `null`, since not every book has a known page count). "Unknown" is `null` only: `Book.totalPage` used to default to `0`, and the `book_total_page_null_drop_stock_status` migration turned existing `0`s into `NULL` and dropped the default. Providers must write `null`, never `0`. The util still skips `0` defensively, because a stray `0` would block every page update — shared by `MyBookService.update` (`currentPage`) and `ReadingLogService.assertLogConsistency` (`endPage`). Don't re-inline this three-part condition; call this instead.
- **Health check** (`src/health`): `GET /health` uses `@nestjs/terminus`'s `PrismaHealthIndicator.pingCheck` against `PrismaService` to confirm DB connectivity. No auth guard — it's meant for infra probes, not end users.

### Auth

`src/auth` implements local (email/password) and Kakao OAuth login, issuing a JWT **access token + refresh token pair as httpOnly cookies** — not a Bearer/Authorization-header scheme, even though `main.ts`'s Swagger `DocumentBuilder` still calls `.addBearerAuth()` (vestigial; ignore it — cookies are the only thing `AccessTokenStrategy` reads).

- `POST /auth/signup|login|kakao/callback` set `access_token` (path `/`) and `refresh_token` (path `/api/auth` only, via `REFRESH_TOKEN_COOKIE_PATH` in [auth.constants.ts](src/auth/auth.constants.ts)) cookies; `POST /auth/refresh` reissues `access_token` from the refresh cookie.
- Two guards in `src/auth/guards`: `AccessTokenGuard` (401 if no/invalid `access_token` cookie — the default for any endpoint requiring a logged-in user) and `OptionalAccessTokenGuard` (never rejects; populates `@CurrentUser()` with `JwtPayload | undefined` when the cookie is missing/invalid). Apply guards **per-method**, not per-controller, when a resource mixes strict writes with anonymous-friendly reads (see `MyBookReviewController`/`ReviewCommentController`) — controller-level and method-level `@UseGuards()` both run (cumulative, not override), so a controller-wide `AccessTokenGuard` would still 401 an anonymous request even if that one method also has `OptionalAccessTokenGuard`.
- `@CurrentUser()` (`src/auth/decorators`) reads `request.user`; its return type reflects which guard is in play (`JwtPayload` under `AccessTokenGuard`, `JwtPayload | undefined` under `OptionalAccessTokenGuard`).
- `signup`/`login`/`kakao/callback` share `AUTH_THROTTLE` (`src/auth/auth.constants.ts`, 5 req/min) — much tighter than the app-wide default (100 req/min, see `app.module.ts` above) since these are the brute-force/spam-signup targets.

### Ownership validation pattern

Every resource is scoped to its owner, but *how* differs based on whether the Prisma model has a direct `userId` column:

- **Direct `userId` column** (`MyBook`, `ReviewLike`, `ReviewComment`, `ReadingGoal`): one atomic query — Prisma's `update()`/`delete()` accept extra scalar filters alongside the unique `where` field, so `prisma.myBook.update({ where: { id, userId }, ... })` checks existence + ownership in a single round trip (see `MyBookService`). `MyBookService.assertOwnership(userId, myBookId)` is the shared existence-check other modules call *before* touching a `MyBook`-scoped resource — `ReadingLogService`, `MyBookReviewService`, and `MyBookTagService` all import `MyBookModule` and call this rather than re-implementing `findFirst({ where: { id, userId } })` locally, since `MyBook` ownership is a rule `MyBookService` (the aggregate owner) should be the single source of truth for.
- **No `userId` column, only reachable via a relation** (`ReadingLog`, `MyBookReview`, `MyBookTag`, and anything hanging off `MyBookReview`): Prisma's `update()`/`delete()` cannot filter through a relation in their unique `where`, only `findFirst`/`findMany` can. So these services do a 2-step **assert-then-mutate**: `findFirst({ where: { id, myBook: { userId } } })` to assert ownership (throwing `NotFoundException` if it misses), then a plain `update({ where: { id } })`/`delete({ where: { id } })` (see `ReadingLogService`, `MyBookReviewService.assertReviewOwnership`, `MyBookTagService`).
- **"Public **or** mine"** access (`MyBookReviewService.accessibleOr`, and the inlined copy in `ReviewCommentService.findOne`) uses an `OR: [{ isPublic: true }, { myBook: { userId } }]` filter. When `userId` is `undefined` (anonymous, via `OptionalAccessTokenGuard`), the owner branch must be **omitted from the array**, not passed as `{ myBook: { userId: undefined } }` — Prisma silently drops `undefined`-valued filter keys, which would turn "owned by me" into "matches any row." The same trap is why `public-review` coerces an anonymous `userId` to the sentinel `0` rather than leaving it `undefined`.
  - This filter answers "**may this actor interact with / see the existence of** this review?" — it is *not* the rule for serving a review's detail. Detail reads are split by audience instead: owner-only in `my-book-review`, public-only in `public-review` (see the module notes below), because the two audiences must receive different fields.

### Domain modules

- **`my-book`**: a user's copy of a book (`MyBook` — status/rating/`currentPage`, unique per `[userId, bookId]`). `MyBookService.buildStatusTransition` encodes the status state machine (`WANT_TO_READ` → `CURRENTLY_READING` → `READ`, with `startedAt`/`finishedAt`/`readCount` side effects); exports `MyBookService` for cross-module use.
- **`reading-log`**: individual reading sessions under a `MyBook`. Creating/updating/removing a `ReadingLog` re-syncs the parent `MyBook` inside the same Prisma transaction via two `MyBookService` methods: `syncProgressFromLatestReadingLog` (recomputes `currentPage`/`lastReadAt` from the *actual* latest log, not the triggering DTO, so edits/deletes of non-latest logs don't corrupt progress) and `startReadingIfWantToRead` (one-directional `WANT_TO_READ` → `CURRENTLY_READING` promotion on first log, create-only). `ReadingLogService` is not exported from `ReadingLogModule`, so nothing outside this module can reuse its ownership check — `quote` below has to do its own instead.
  - **`date` is a date, not an instant, and it is load-bearing.** It's the day the *user* picked for the session (a 23:00–01:00 session belongs to whichever day they say), so it is deliberately **not** derived from `startTime`. It arrives as a `'YYYY-MM-DD'` string and `toRecordDate` converts it to **UTC midnight** — accepting a midnight ISO datetime instead would silently shift the day, since `new Date(2025, 11, 11).toISOString()` is `'2025-12-10T15:00:00.000Z'` in KST and `@db.Date` truncates in UTC. Two guards go with it: the parse round-trips (`'2025-02-30'` otherwise rolls over to March 2 instead of erroring), and future dates are rejected — `date` is the **first** `orderBy` key in `syncProgressFromLatestReadingLog`, so one log dated 2099 would win "latest" forever and freeze `currentPage`.
  - `readingMinutes` is derived from `startTime`~`endTime`, never accepted from the client (it used to be, and could contradict the timestamps). `update` recomputes it whenever either time changes. `readingMood` (an enum) was removed entirely — emotions don't enumerate, it grew to 12 values, became nullable under input friction, and nothing ever filtered or aggregated it; feelings now go in the free-text `memo`. Before reintroducing any structured field here, build the screen that aggregates it first.
  - `findAll` scopes by `myBook: { userId }` **always**, with `myBookId` as an optional narrowing filter (omit it for the cross-book timeline/calendar view) and optional `from`/`to` date filters. Query-range parsing (`parseDateOnly`) deliberately allows future dates — unlike recording a session, asking for "through the end of this month" is legitimate. List items carry `book` (title/thumbnail) because a cross-book list can't identify a book from `myBookId` alone.
- **`quote`**: highlights/quotes saved during a `ReadingLog` session. `Quote` has no direct `userId` and isn't even directly under `MyBook` — ownership is two relations deep (`Quote` → `ReadingLog` → `MyBook` → `userId`). `QuoteService.assertReadingLogOwnership` does its own `findFirst({ where: { id: readingLogId, myBook: { userId } } })` rather than reusing `MyBookService.assertOwnership` (wrong level — that checks a `MyBook` id, not a `ReadingLog` id) or `ReadingLogService` (not exported, see above).
- **`my-book-review`**: one public/private one-line review per `MyBook` (unique `myBookId`). This module is the **owner-facing** side of a review — every endpoint here requires `AccessTokenGuard` and only ever touches the caller's own reviews. `findAll` (everything the caller wrote, `isPublic` irrelevant), `findLiked`/`findCommented` (reviews the caller liked/commented on, filtered through `accessibleOr` so a review that went private afterward silently drops out of these lists). `GET /my-book-review/:id` is **owner-only** (`where: { id, myBook: { userId } }`) and returns the management shape (`myBookId`/`isPublic`/`updatedAt` — the fields the edit UI needs); reading *someone else's* public review is `GET /public-review/:id` instead, because a stranger must get `author`/`isLiked` and must **not** get the internal `myBookId`. Don't "helpfully" widen `findOne` back to `accessibleOr` — that reintroduces the leak. Exports `MyBookReviewService` (`assertAccessible`) for `review-like`/`review-comment` to reuse.
  - Within this module `accessibleOr` now has exactly one caller, `assertAccessible` — "may this actor like/comment on this review?", which is a different question from "may this actor read this review's detail?". Keep the two apart.
- **`review-like`** / **`review-comment`**: interactions on a `MyBookReview`. Both import `MyBookReviewModule` and call `assertAccessible` before writing, so liking/commenting is only possible while the target review is currently public (or owned by the actor) — flipping a review to private blocks *new* interactions immediately but doesn't retroactively delete existing `ReviewLike`/`ReviewComment` rows.
  - `ReviewComment` responses expose the commenter as `author` (`{ id, name, profile }`), mapped from the `user` relation, and deliberately omit the raw `userId` — "is this my comment?" is answered by `author.id`. The join **must** go through `ReviewCommentSelect` (`review-comment.constants.ts`): `User` holds `password`/`email`/`birthday`/`gender`, so a bare `include: { user: true }` dumps the password hash straight into the API response. Same rule as `MyBookTagSelect`/`chosung` below — never let a `User` relation reach a response without an explicit `select`.
- **`public-review`**: the cross-user **reader-facing** side of reviews (`OptionalAccessTokenGuard` on the whole controller — anonymous browsing is the point of "public"). `GET /public-review` is the feed; `GET /public-review/:id` is the detail view for *anyone's* public review, and both return the same item shape — `author`, `isLiked`, `rating`, and `book` (title/thumbnail/**isbn**), with `myBookId`/`isPublic` withheld. `rating` rides along because `isPublic` means "publish my *impression* of this book", and an impression is the one-liner plus the score; `currentPage`, reading logs and quotes are personal records and stay private, so `myBook`'s select is kept to exactly `rating` + `book` + `user`. `isbn` is included so a feed card can link to the book page. The detail endpoint filters on `where: { id, isPublic: true }` with **no** owner branch — a private review is invisible here even to its author, who reads it through `my-book-review` instead. Filters by `isbn`, not the internal `Book.id` — no endpoint ever exposes `Book.id` to a client, since book detail pages are keyed by ISBN. Computes `isLiked` per item via a single query (nested `reviewLike: { where: { userId }, take: 1 }` select, not a second round trip); for anonymous requests, `userId` is coerced to the sentinel `0` (never a real autoincrement id) rather than `undefined`, for the same Prisma-drops-`undefined` reason noted above.
- **`public-tag`**: `GET /public-tag?isbn=&limit=` (no guard, `limit` 1–50, default 20) — cross-user tag popularity for the FE tag cloud on the book detail page (`/search/:isbn`); `isbn` narrows the aggregate to that book's `MyBook`s (omit it for the global aggregate), normalized via `normalizeIsbn13` like `CreateMyBookDto` — an unparseable ISBN is transformed to `false` rather than `null` because `@IsOptional` treats `null` as absent and would silently fall back to the global aggregate instead of 400. A book nobody has shelved returns `[]`, not 404. Returns `[{ tagId, value, count }]` where `count` is the number of `MyBook`s carrying the tag, ordered `count DESC, tagId ASC`. Only tags used by at least `PUBLIC_TAG_MIN_DISTINCT_USERS` (2) **distinct users** are included (within one book `MyBook` is unique per `[userId, bookId]`, so there this is simply `count >= 2`): `Tag.value` is free text a user typed into their own shelf, so ranking by `count` alone would publish one person's private tag (e.g. a family member's name) as soon as they put it on enough books. That distinct-user filter isn't expressible in Prisma `groupBy`, so this is the one service using `$queryRaw` (via `Prisma.sql`, so the spec can assert the SQL + bound values); `COUNT(*)` comes back as `BigInt` and must be converted to `number` before it hits the JSON response.
- **`tag`** / **`my-book-tag`**: `Tag` is a shared, deduplicated vocabulary (unique `value`) with no owner and no direct create/delete endpoint — it's only ever created via `TagService.findOrCreate` (an `upsert` + P2002-catch-and-refetch, mirroring `BooksService.findOrCreate`'s race handling), invoked from `MyBookTagService.create` when a user attaches a not-yet-existing tag value. `GET /tag?query=` powers client-side autocomplete and matches against both the literal `value` and a `chosung` column (Korean initial-consonant string, e.g. "자기계발" → "ㅈㄱㄱㅂ", extracted via `es-hangul`'s `getChoseong`) with an `OR` filter — `chosung` is an internal search-only column and must always be excluded from responses via an explicit `select` (see `MyBookTagSelect` in `my-book-tag.constants.ts`), never left to leak through a bare `findMany`/`include`. `MyBookTag` (the per-`MyBook` attachment, unique `[myBookId, tagId]`) deliberately does **not** cascade-delete its `Tag` when the last reference is removed — `MyBookTag.tag` has `onDelete: Cascade`, so an inline "delete if orphaned" check in the same request would race against a concurrent attach on another request and could cascade-delete that other request's brand-new row; orphaned `Tag` cleanup, if ever needed, belongs in a separate batch job instead.
- **`reading-goal`**: yearly (`month: null`) or monthly per-metric reading targets (`ReadingGoalMetric`: `BOOK_COUNT`/`PAGE_COUNT`/`MINUTES`), unique per `[userId, year, month, metric]`. Has a direct `userId` column like `MyBook`, so `ReadingGoalService` uses the same 1-step atomic `update()`/`delete()` pattern (no `MyBookService` involved — a `ReadingGoal` isn't scoped to a `MyBook`). `year`/`month`/`metric` are treated as immutable identity once created (excluded from `UpdateReadingGoalDto`) — changing which period/metric a goal targets means delete + recreate, not update.
- **Books module** (`src/books`): `BooksController` exposes book search/detail; `BooksService` does local `Book` lookup/creation against Prisma. External metadata comes from two provider services under `src/books/providers/{kakao,aladin}`, each following the same shape — inject `HttpService` (`@nestjs/axios`) + `ConfigService`, call the external API with `firstValueFrom`, `catchError` into a `BadGatewayException`, and map the raw response into a local DTO via a static `.from(...)`. Provider exports are re-exported through `src/books/providers/index.ts`. These providers need `KAKAO_REST_API` and `ALADIN_TTB_KEY` env vars (see [.env.example](.env.example)).
  - **Search results vs `Book`.** `GET /books` (Kakao search) returns a throwaway **candidate list**. `Book` is the **canonical record**, keyed by ISBN-13. The only thing that crosses from one to the other is the normalized `isbn`: shelving sends `isbn` alone (`CreateMyBookDto`), and the server re-fetches the metadata. So the two may differ in *detail* (cover size, description length, page count added from another source), but never in *which book it is*. That is why ISBN/ISSN classification lives on the server, not the client.
    - Each search item carries `isbn: string | null`, a normalized ISBN-13 (`null` when the item isn't an ISBN book), plus `identifierType: 'ISBN' | 'ISSN' | 'UNKNOWN'`. These are flat fields, not a nested `identifier` object, so they match every other endpoint's `isbn`. They are derived by `parseKakaoIdentifier` (`kakao-identifier.util.ts`), whose doc comment lists the real Kakao `isbn` formats.
    - `parseKakaoIdentifier` checks the 13-digit token first, and if that token is an ISSN (`977…` EAN-13) it **never** falls back to the 10-digit token. In `"1228402000 9771228402006"` the 10-digit part is derived from the ISSN, yet it passes the ISBN-10 checksum; isbn3 would turn it into the unrelated `9781228402005`.
    - `normalizeIsbn13` (common) stays strict and rejects the combined Kakao form. It validates user input; Kakao's quirks are handled only in the Kakao provider.
    - ISSN/UNKNOWN items are **kept** in the list, marked but not filtered out, so page sizes stay consistent with `meta`.
    - `pubDate` is sent as `'YYYY-MM-DD'`, not Kakao's KST-midnight `datetime` (`…T00:00:00.000+09:00`). A client in another timezone would otherwise render the previous day.
    - Pagination `meta` is computed from `min(pageable_count, KAKAO_MAX_PAGE * size)`, never `total_count`, and Kakao's `is_end` overrides `hasNextPage`. Verified live: `pageable_count` caps at 1000 (`"소설"`: `total_count` 79265). Requesting past the last page makes Kakao silently repeat the last page, so a `total_count`-based `hasNextPage` makes infinite scroll loop on duplicates.
  - **Aladin → 국립중앙도서관 migration (Aladin API shuts down; Aladin stays in use until 2026-10-30).** `src/books/providers/nl` (`NlBookSearchService`/`NlLookupResDto`, env `NL_CERT_KEY`) is the replacement for ISBN lookup, but it is intentionally **not yet registered in `BooksModule`** or referenced by `BooksService`/`BooksController`. The switch is: swap `AladinBookSearchService`/`AladinLookupResDto` for the NL ones in `BooksService`, `BooksController`, `BooksModule` and `books.service.spec.ts`, then delete `providers/aladin` and `ALADIN_TTB_KEY`. NL differs from Aladin in a few ways, all checked against the live API on 2026-09-30. The DTO spec's fixtures are real responses.
    - An auth error comes back as HTTP 200 `{ RESULT: 'ERROR', ERR_CODE: '011', ERR_MESSAGE }` with no `docs`, so it maps to a `BadGatewayException`, not a 404. A missing ISBN is `{ TOTAL_COUNT: '0', docs: [] }` → 404.
    - `isbn` is a prefix search, so the result is picked by exact `EA_ISBN` match.
    - `pubDate` prefers `REAL_PUBLISH_DATE` over `PUBLISH_PREDATE` (the CIP "planned" date). Both are `yyyymmdd`, parsed to UTC midnight.
    - `TITLE` carries a subtitle after ` : `, and `splitTitle` separates it.
    - **`TITLE_URL` (cover) was empty in every record sampled**, so `thumbnail`/`coverImage` are effectively always `null`.
    - Recent paper books usually have `PAGE` (`'393 p.'`) and `BOOK_INTRODUCTION`. Older books (e.g. a 2014 title) can have almost everything empty: page, dates, cover, intro.
    - There is no url.
  - `src/books/providers/data4library` (`Data4LibraryBookSearchService`/`Data4LibraryLookupResDto`, env `DATA4LIBRARY_AUTH_KEY`) is a second ISBN-lookup candidate from 도서관 정보나루 (`https://data4library.kr/api/srchDtlList`; it works over HTTPS, so don't send the key over `http://`). It is also **not wired** yet and has the same `getByIsbn` → `Book`-shaped DTO contract, so either one can be swapped in. The DTO spec's fixture is the real response for `9788996991342`. Errors come back as HTTP 200 `{ response: { errCode, error } }` (`authErr`), and these map to 502. Things the real data showed:
    - It has **no page count**, so `totalPage` is always `null`.
    - `publication_date` is usually just a year (`'2014'`), so `pubDate` is usually `null`. A year is never padded to Jan 1.
    - `bookname` carries the subtitle after ` :`, and `splitTitle` separates it.
    - `authors` is `'기시미 이치로,전경아 옮김'`: no `;`, and the author role word is dropped.
  - Shared parsing lives in `src/books/providers/book-metadata.util.ts`: `splitAuthorsByRole`, `parseUtcDate` and `splitTitle`. Don't re-inline them per provider. `splitAuthorsByRole` groups by `;` when the string has one (NL: the role word applies to the whole group). Otherwise it treats each `,`-separated name as its own group (정보나루: the role word applies only to the name it follows). So a 정보나루 co-translation `'A, B 옮김'` files A as an author, and the string alone can't tell the two readings apart.

### Testing

Unit tests live alongside source as `*.spec.ts` (jest rootDir is `src`). E2E tests live under [test/](test/) as `*.e2e-spec.ts`, run through a separate Jest config ([test/jest-e2e.json](test/jest-e2e.json)) with its own rootDir/moduleNameMapper, and boot the real `AppModule` (same `ValidationPipe`/`cookie-parser`/`api` prefix setup as `main.ts`) against the local MySQL from `docker-compose.yml` — `npm run prisma:migrate` must be up to date before running them. Every domain service has a co-located spec (the only service without one is the `PrismaService` lifecycle wrapper); controllers, guards, pipes and interceptors have no unit coverage by design — [test/auth.e2e-spec.ts](test/auth.e2e-spec.ts) is where `AccessTokenGuard`/`RefreshTokenGuard` actually get exercised (signup → login → `/auth/me` → refresh → logout over real httpOnly cookies), since a guard can't be meaningfully unit-tested against a mocked Prisma the way a service can.

- **Shared helpers** live in `src/common/testing/test-helpers.ts` (`createPrismaError`, `firstCallArg`, `callWhere`, `callData`, `fakeAxiosResponse`). They are test-only: **not** re-exported from `src/common/index.ts`, and `src/common/testing` is in `tsconfig.build.json`'s `exclude` so they never reach `dist`. Import helpers from there rather than redefining them per spec.
- **Mocked Prisma does not evaluate `where`.** A test that only asserts on `data` will still pass after the `userId`/relation filter is deleted from the query — i.e. the ownership rule silently stops being tested. So whenever a query carries an authorization condition, assert the argument itself with `callWhere(...)`. This is the single easiest way to write a test that looks thorough and protects nothing.
- Prefer driving private logic through the public method that uses it (e.g. `buildStatusTransition` is tested via `update`, `accessibleOr` via `assertAccessible`) instead of reaching into internals.
- Because Prisma is mocked, these tests say nothing about real queries, DB constraints, or `$transaction` rollback — a mocked `$transaction` only proves the calls were made with the same `tx`, not that they roll back together. Anything that depends on actual atomicity or on Guards/Pipes/Interceptors (all at 0% unit coverage) belongs in e2e.

ESLint config is flat-config style ([eslint.config.mjs](eslint.config.mjs)) using `typescript-eslint` + `eslint-plugin-prettier`; Prettier config is in [.prettierrc](.prettierrc) (single quotes, trailing commas).
